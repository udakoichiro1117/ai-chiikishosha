# AI地域商社

関西の生産者と飲食店を、AIと確実なロジックでつなぐ仕入れマッチングサービスです。

🔗 公開URL: https://ai-jimoseri.vercel.app/

---

## 概要

### 解決したい課題

飲食店と生産者は、どちらも「つながりたい」のに、その情報がどこにもまとまっていません。

- **飲食店側**: 普段使っている市場や卸以外に、どの農家に何がどれだけあるのか知る手段がない。欲しい食材が1軒で揃わない場合、複数の仕入れ先を自分で探して組み合わせる必要がある。
- **生産者側**: 少量だったり規格外(形が不揃い・余剰分)だったりして、本来は売れるはずなのに販路を自分で開拓できない食材がある。飲食店を探し、営業し、条件を調整する負担が大きい。

市場や卸、地域商社、ベジマチや食べチョクProのような既存のマッチングサービスも「探す」ところまでは支援してくれますが、見つかった後に「本当に欲しい数量が揃うか」「価格や受け渡し条件は合うか」「足りなければ他の農家と組み合わせる必要があるか」を確認・調整するのは、結局人の手作業に委ねられています。

### このアプリがやること

飲食店が欲しい食材・量・条件を自然な文章で入力するだけで、

1. AIが文章を読み取り、品目・数量・希望日・地域などの条件に構造化する
2. 実際に出品されている食材の中から、条件に合う生産者を抽出する
3. 1軒で量が足りない場合は、関わる農家の数が最も少なくなる組み合わせを確実なロジックで自動算出する
4. その場で生産者ごとに仕入れを依頼でき、生産者は個別に承諾・却下できる

という一連の流れを、画面を行き来することなく完結させます。AIは「言葉を読み取る」ところに徹し、数量の計算・組み合わせの判断・在庫の整合性確認は、再現性のある通常のプログラムが行います。

生産者側は、トマトのような定番品目に限らず自由な品目名で出品でき、写真・音声・テキストのいずれからでも出品内容を入力できます。規格外品や余剰分にも自分で値段をつけて出品できるほか、期限が近い食材を品目を問わず近隣の飲食店に提案する「おまかせ救済」機能もあります。

## 使い方

### デモとして触ってみる

公開URL(https://ai-jimoseri.vercel.app/)を開くとログイン不要ですぐに試せます。

1. ホーム画面で🏪「飲食店」を選ぶ
2. 「欲しい食材・数量・受取条件を伝える」画面にある **「【デモ用】明後日までに大阪近郊のトマトを10kg、形不揃いOK を入力」** ボタンを押す(内蔵デモの生産者データと品目・数量・日付がぴったり一致するよう作られた文章が自動入力される)
3. 「AIで読み取る」→ 内容を確認 → 「仕入れ案を作る」と進めると、複数の農家を組み合わせた仕入れ案が表示される
4. 「この内容で仕入れを依頼する」まで進めば、実際の注文(生産者による承諾/却下)の流れまで一通り試せる

生産者側(🌾「生産者」)では、農園情報を登録した後、写真撮影・音声入力・自由記述のいずれかで出品内容を入力できます。

ログインはメールアドレス宛のワンタイムリンク方式(マジックリンク)で、パスワードは使いません。ログインすると、出品・注文・受取条件/農園情報をどの端末からでも引き継げます(未ログインの場合は端末ごとの匿名IDでのみ管理されます)。

### ローカルで動かす

このリポジトリは、フロントエンド(Vite)とバックエンド(Vercelのサーバーレス関数)が同じプロジェクトに同居しています。API(`api/`以下)はVercel特有の実行方式に依存しているため、素の`vite`だけでは動かず、**Vercel CLIでのローカル実行が前提**です。

```bash
npm install
npm i -g vercel        # 未導入の場合
vercel dev              # api/ を含めてローカルで実行(既定: http://localhost:3000)
```

フロントエンドだけを素早く確認したい場合は `npm run dev` (Vite単体、ポート5173)でも起動できますが、`vite.config.js`で `/api` への呼び出しは `http://localhost:3000` にプロキシされる設定になっているため、API機能を使うには別途 `vercel dev` を起動しておく必要があります。

### 環境変数

Vercel Blobを除き、いずれも未設定のまま動かせます(該当機能がグレースフルに無効化されるか、ルールベースの代替処理にフォールバックします)。

| 変数名 | 必須 | 用途 |
|---|---|---|
| `BLOB_READ_WRITE_TOKEN` | ほぼ必須 | 出品・注文・拠点・メッセージ等の共有データストア(Vercel Blob)への読み書き。Vercelプロジェクトに Blob Store をアタッチすると自動で設定される |
| `GEMINI_API_KEY` | 任意 | 自然文・音声・写真からの条件抽出(Gemini API)。未設定時はルールベースの正規表現抽出(`src/parser.js`)に自動フォールバック |
| `GEMINI_MODEL` | 任意 | 使用するGeminiモデル名を上書き(既定値あり) |
| `RESEND_API_KEY` | 任意 | ログイン用マジックリンクのメール送信(Resend API)。未設定時はログインリンクの送信自体が失敗する(匿名利用は引き続き可能) |
| `RESEND_FROM_EMAIL` | 任意 | 送信元メールアドレス(既定:`onboarding@resend.dev`。実運用では独自ドメインの検証が必要) |
| `ADMIN_EMAILS` | 任意 | カンマ区切りのメールアドレス一覧。ここに含まれるアカウントは「1メールアドレス=1役割固定」のルールを例外として、飲食店・生産者どちらの役割でもログインできる |
| `DEMO_ADMIN_KEY` | 任意 | デモ運営者向け機能(出品・注文等のスナップショット保存/復元)の照合キー |

### ビルド

```bash
npm run build     # dist/ に静的ファイルを出力(Viteのビルドのみ。api/は含まない)
npm run preview   # ビルド結果をローカルで確認
```

本番デプロイは `vercel --prod`(またはGitHub連携によるVercelの自動デプロイ)で行います。

## 技術構成

### 全体構成

- **フロントエンド**: ビルドツールなしのバニラJS SPA(フレームワーク不使用)。`src/main.js`が唯一のエントリポイントで、アプリ全体の状態(`state`)を1箇所で保持し、`render()`が`#app`の`innerHTML`を毎回丸ごと描き直す素朴な構成。仮想DOMやコンポーネント分割は採用していない。
- **バックエンド**: Vercel Functions(`api/*.js`)。各ファイルが`export default async function handler(req, res)`形式のサーバーレス関数として、同一ドメインの`/api/*`にそのままデプロイされる。
- **データストア**: [Vercel Blob](https://vercel.com/docs/storage/vercel-blob)。RDBや専用DBは使わず、1件のレコード=1個のJSONファイルとしてBlobに保存する(例:出品1件なら`listings/<id>.json`)。読み取りは`access:'private'`+`useCache:false`を徹底し、キャッシュ起因の古いデータ表示を避けている。
- **ホスティング**: Vercel。GitHubリポジトリと連携し、pushで自動デプロイされる。

### 主要な外部サービス(すべて任意・疎結合)

| サービス | 用途 | 無い場合の挙動 |
|---|---|---|
| Google Gemini API | 自然文・音声テキスト・写真からの条件抽出 | `src/parser.js`のルールベース抽出(正規表現・キーワード一致)に自動フォールバック |
| Resend | ログイン用マジックリンクのメール送信 | ログインリンク送信が失敗扱いになる(匿名利用は継続可能) |
| 国土地理院 住所検索API | 住所→緯度経度のジオコーディング(無料・APIキー不要) | 失敗時は地域名の文字列一致によるマッチングに自動で切り替わる |
| zipcloud | 郵便番号→住所の自動入力(無料・APIキー不要) | 自動入力ボタンが使えないだけで、手入力は可能 |
| Leaflet + OpenStreetMap | 仕入れ案結果画面の地図表示 | 座標が無い場合は地図セクション自体を表示しない |

### マッチングロジックの設計方針(AIと通常のロジックの役割分担)

このアプリで最も意識している設計方針は、**AIに任せる範囲をあえて狭めること**です。

- AI(またはそのルールベース代替)が行うのは、自然文・音声・写真を構造化データ(品目・数量・単位・希望日・地域など)に変換するところまで。
- 実際にどの生産者を組み合わせるか、数量が条件を満たすか、金額はいくらになるかは、`src/matching.js`の`computeAllocation()`が担う。候補数が少ないデモ規模を前提に、条件に合う生産者の全組み合わせを列挙し、希望量をちょうど満たす組み合わせの中から「関わる農家の数が最も少ない」ものを選び、同数の候補があれば総額が最も低いものを採用する。
- 判定に使った理由(除外理由・組み合わせを選んだ理由)は、推測ではなく実際の判定ロジックの結果としてそのまま画面に表示される。

この役割分担により、AIの出力が多少揺らいでも、金額や数量の計算結果自体は常に再現可能・検証可能になっている。

### 所有権・ログインの仕組み

- 端末ごとにローカルストレージへ匿名UUIDを保持し、これを`ownerId`として出品・注文を紐付ける(ログイン不要で即座に利用開始できる)。
- メールアドレス宛のワンタイムリンク(`api/auth.js`)でログインすると、以降は検証済みメールアドレスが`ownerId`として使われる。サーバー側の所有権チェックは「文字列が一致するか」だけを見ており、それが匿名UUIDかメールアドレスかを区別していないため、ログインは「`ownerId`として使う値を切り替えるだけ」で実現している。
- 1メールアドレスにつき役割(飲食店/生産者)は一度登録すると固定だが、`ADMIN_EMAILS`に含まれるアカウントのみ例外として両方の役割を行き来できる。
- ログイン済みアカウントは、受取条件・農園情報もサーバー(`api/profile.js`)に保存され、別端末からログインしても引き継がれる。

### ディレクトリ構成

```
.
├── index.html            # SPAのエントリHTML
├── vite.config.js        # /api を http://localhost:3000 にプロキシするだけの最小構成
├── src/
│   ├── main.js           # 状態管理・画面描画・イベント処理(アプリ本体)
│   ├── data.js           # デモ用初期データ、品目/地域の選択肢
│   ├── matching.js       # 複数生産者の組み合わせを算出する確実なロジック
│   ├── parser.js         # AIが使えない場合のルールベース自然文抽出
│   ├── rescue.js         # 「おまかせ救済」(品目を問わない近隣の余剰提案)の抽出ロジック
│   ├── freshness.js      # 品目カテゴリ別の鮮度期限(出荷可能日+日数)の算出
│   ├── geo.js            # 住所→緯度経度のジオコーディング、距離計算
│   ├── map.js            # 仕入れ案結果画面のLeaflet地図表示
│   └── style.css
└── api/
    ├── listings.js       # 出品(生産者の出品情報)のCRUD、デモデータの自動補充
    ├── orders.js         # 注文(仕入れ依頼・承諾/却下・数量修正)
    ├── hubs.js           # 共通受渡拠点(複数生産者が使える受け渡し場所)のCRUD
    ├── messages.js       # 注文明細ごとの個別メッセージ(受け渡しの相談用)
    ├── auth.js           # メールアドレスのワンタイムログインリンク(発行・検証)
    ├── profile.js        # ログイン済みアカウントの受取条件・農園情報のサーバー保存
    ├── parse.js          # Gemini APIへの自然文・写真解析リクエストの代理
    └── snapshot.js        # デモ運営者向け:共有データのスナップショット保存/復元
```
